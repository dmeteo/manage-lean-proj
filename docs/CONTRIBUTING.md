# Правила совместной работы

Документация v0.1, 26.11.2026. Приложение не реализовано. Публичный репозиторий не должен содержать оригиналы внутренних материалов, персональные данные, пароли, токены, .env, пользовательские файлы и копии БД.

## Ответственность

Frontend владеет frontend/, интерфейсами, MSW и UI/E2E-проверками. Backend — backend/, БД, API, правами, файлами и развёртыванием. Тимлид — требованиями, согласованиями с заказчиком, бэклогом, приёмкой и защитой. Изменения docs/API_CONTRACT.md требуют проверки обоих разработчиков, бизнес-правила — также тимлида. Не менять чужой каталог без обсуждения затронутого контракта.

## Ветки и коммиты

main — интеграционная ветка. Не пушить код напрямую, не применять force push и не переписывать историю коллег. Исключение для пустого репозитория: первичная инициализация только .gitignore, необходимая как база PR документации.

Короткие ветки от актуальной main: docs/backend-contract-v01, feat/frontend-projects, feat/backend-projects, fix/backend-access. Каждая решает одну целостную задачу. После согласования контракта оба разработчика начинают свои ветки от одного зафиксированного SHA. Независимость обеспечивается каталогами и API, а не долгоживущими расходящимися frontend/backend-ветками.

Коммиты: docs: описать API; feat(frontend): добавить реестр; fix(backend): запретить чужой файл. Не включать незапрошенные изменения, секреты, сборки и локальные данные. Перед коммитом просмотреть diff и список файлов. Конфликт решает владелец соответствующего модуля, не удаляя изменения другого участника.

## Pull Request

PR содержит проблему, итоговое поведение, связанные FR/задачи, затронутую версию API, фактически выполненные проверки и ограничения. UI-изменения сопровождаются снимками, API — примерами запросов/ответов и влиянием на MSW. Если проверки не выполнены — указать причину.

Автор не принимает собственную работу за независимое ревью. Минимум один другой участник проверяет PR; контракт смотрят оба разработчика, требования подтверждает тимлид. main не сливается до разрешения замечаний и обязательных проверок. Настройка branch protection рекомендована владельцу репозитория; автоматически настроенной её не считать. После merge удалить только свою завершённую ветку по договорённости.

## Изменение API и архитектуры

1. Backend проводит ревью по шаблону BACKEND_SPEC до написания приложения.
2. Замечания оформляются в PR: текущий вариант → точная замена → причина → влияние на фронт, БД и сроки.
3. Frontend проверяет DTO, nullable, статусы, ошибки, файлы и сценарии MSW.
4. Тимлид фиксирует ответы заказчика по D2–D7 и методике; отсутствие ответа не означает согласие.
5. Обновляются BACKEND_SPEC, API_CONTRACT и ROADMAP в одном PR.
6. После явных согласований фиксируются версия и merge SHA. Backend формализует OpenAPI, frontend обновляет fixtures/MSW. Только после этого начинается код.
7. Несовместимые изменения согласуются до внедрения и переходят синхронно; ни один участник не меняет enum/поля только у себя.

Архитектурные решения первой итерации вести в разделе D1–D10 BACKEND_SPEC: дата, авторы согласования, вариант, причина, последствия, ссылка на PR. При росте объёма допускаются отдельные ADR в docs/decisions/, сейчас дополнительные файлы не нужны. Микросервисы и интеграции без доказанной потребности не добавлять.

## Параллельная разработка и передача результата

Frontend после согласования разрабатывает на MSW; backend реализует те же сценарии на сервере. Backend передаёт URL стенда, SHA, версию контракта, OpenAPI, миграции, инструкцию запуска, синтетические данные, результаты API-проверок и список ограничений. Пароли — отдельно безопасным способом.

Frontend передаёт SHA, экраны/сценарии, версию MSW, проверенные ошибки/роли, результаты E2E и дефекты. Тимлид связывает FR с PR, приёмочным сценарием и результатом на стенде. Передача считается завершённой, когда получатель воспроизвёл запуск/сценарий и записал результат; сообщение «готово» не заменяет проверку.

Порядок интеграции: login/me/logout и CSRF → проекты → мероприятия/план-факт → файлы/две проверки → внешний статус → KPI/CSV/аудит. MSW отключается явно; реальный запрос и сохранение в БД проверяются. Не выдавать mock за готовый backend.

## Проверки и завершение

Для backend обязательны права двух предприятий, переходы, сроки, файлы, конкурентные изменения и чистый запуск. Для frontend — формы, состояния загрузки/пустоты/ошибки, разрешённые действия и E2E. Сквозной сценарий выполняется на реальном API с перезапуском и повторным чтением данных. Полный список — BACKEND_SPEC, раздел 7.

Каждый результат содержит дату, SHA, среду, ожидаемое/фактическое и оставшиеся дефекты. Проверки документации и приложения учитываются отдельно. Журнал ИИ пополняется реальными действиями и человеческими исправлениями; не придумывать время, долю кода, тесты и одобрения. Публичные скриншоты обезличивать.
