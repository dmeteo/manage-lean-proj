# Backend: рабочее задание v0.1

**Статус: проект для обязательного ревью, 26.11.2026. Программирование пока не начинать.**

Перед началом программирования backend-разработчик должен:

1. Полностью изучить техническую документацию.
2. Проверить архитектуру и модель данных.
3. Проверить API-контракт.
4. Выявить противоречия, ошибки и недостающие требования.
5. Предложить улучшения с аргументацией.
6. Оценить трудоёмкость реализации.
7. Определить технические риски.
8. Согласовать изменения с frontend-разработчиком.
9. Зафиксировать согласованный контракт.
10. Только после этого приступить к реализации.

Архитектура ниже предварительная. Допустимо предложить более простое решение с оценкой последствий. Общие правила и DTO — в [API_CONTRACT](API_CONTRACT.md), сроки — в [ROADMAP](ROADMAP.md).

## 2. Предлагаемая архитектура

Один модульный монолит: ASP.NET Core Web API на C#, EF Core, PostgreSQL, Docker Compose для локального и демонстрационного запуска. Версии SDK, БД и пакетов backend выбирает и фиксирует при ревью; совместимость проверяется до установки. REST/JSON с префиксом /api, OpenAPI после согласования.

Логические слои в одном приложении: HTTP/DTO → прикладные операции и проверки прав → EF Core/файловое хранилище. Модули: доступ, проекты, мероприятия/согласования, файлы, показатели, отчёты/аудит. Не требуются микросервисы, брокер, CQRS, отдельный универсальный репозиторий или распределённые транзакции.

Изменение состояния и AuditEvent записываются одной транзакцией БД. Файлы лежат в закрытом постоянном томе; БД хранит метаданные и случайный storageKey. При сбое между записью файла и БД удалять незарегистрированный объект; скачивание разрешать только после успешной фиксации метаданных. Очистку и восстановление проверять отдельно.

## 3. Предлагаемая модель данных

Все ID — UUID. Все внешние ключи обязательны, кроме явно nullable; удаление зависимых бизнес-данных каскадом запрещено. Длины и DTO определены контрактом. Изменяемые агрегаты имеют version int, createdAt/updatedAt UTC.

| Сущность | Атрибуты и связи |
|---|---|
| Enterprise | id, name; 1:N с Project и пользователями предприятия |
| User | id, displayName, уникальный нормализованный login, passwordHash, role, enterpriseId nullable для РЦК, isActive; пароль не возвращается |
| Project | id, name, enterpriseId, managerId, approverId, startDate, plannedEndDate, actualEndDate nullable, goal/problem/description, status, archivedFromStatus nullable, version |
| ProjectMember | projectId + userId уникальны; явный доступ сотрудника предприятия к проекту |
| Activity | id, projectId, title, stage nullable, assigneeId, plannedStartDate nullable, plannedEndDate, actualEndDate nullable, status, isRequired, requiresDocument, sortOrder, comment nullable, externalStatus, externalRecordedAt/By/comment nullable, version |
| Document | id, activityId, originalName, storageKey, mediaType, sizeBytes, uploadedBy, uploadedAt, kind, revision; новая загрузка создаёт новый id, старый файл сохраняется |
| Review | id, activityId, cycle, stage (manager/approver), actorId, decision, comment nullable, createdAt; неизменяемая история |
| Metric | id, projectId, name, unit, plan nullable, actual nullable, recordedDate, source nullable, version |
| EconomicEffect | id, projectId, type, amount, currency, periodStart/End, calculationDocumentId nullable, confirmationDocumentId nullable, version |
| AuditEvent | id, actorId, entityType/id, action, timestamp, changeSummary; без паролей, токенов и содержимого файлов |

Project → Activity 1:N; Activity → Document/Review 1:N; Project → Metric/EconomicEffect 1:N. Документ расчёта/подтверждения должен принадлежать мероприятию того же проекта. Исполнитель активен, относится к предприятию проекта и включён в ProjectMember. managerId и approverId — активные пользователи соответствующих ролей РЦК. В MVP у пользователя одна роль. Проект может иметь несколько сотрудников через ProjectMember.

Предлагаемая альтернатива на ревью: единая таблица KPI с видами эффекта проще по числу таблиц, но смешивает денежные и натуральные показатели; отдельные Metric/EconomicEffect яснее по валидации. Не вводить универсальный конструктор полей.

## 4. Матрица доступа

Обозначения: К — все проекты; РП — назначенный руководитель; С — назначенный согласующий; И — сотрудник своего предприятия, включённый в проект. Админ не получает бизнес-права автоматически.

| Действие | admin | coordinator | manager | approver | employee |
|---|---|---|---|---|---|
| Пользователи и предприятия | да | чтение справочников | чтение доступных | чтение доступных | чтение своего |
| Создать проект, назначить РП/С, участников | нет | К | нет | нет | нет |
| Читать проект/мероприятия/файлы | нет | К | РП | С | И |
| Изменить карточку/мероприятия | нет | назначения | РП | нет | факт/комментарий своего задания |
| Загрузить файл | нет | нет | РП | нет | своё задание |
| Отправить на проверку | нет | нет | нет | нет | своё задание |
| Первичная проверка | нет | нет | РП | нет | нет |
| Внутреннее утверждение | нет | нет | нет | С | нет |
| Внести внешний статус | нет | К | нет | нет | нет |
| KPI/эффект | нет | чтение К | запись РП | чтение С | чтение И |
| Сводка/CSV | нет | К | РП | С | И |
| История | все метаданные аудита | К | нет | нет | нет |

Права проверяются на сервере для каждого запроса, включая списки, вложенные ресурсы, скачивание и экспорт. Неизвестный или чужой объект → 404; известный доступный объект, запрещённое действие → 403. Фильтр применяется до пагинации/агрегации. Сотрудник А не получает данные Б даже по прямому UUID. Публикация личных данных в demo запрещена.

Авторизация: предлагается серверная cookie-сессия, HttpOnly/Secure/SameSite=Lax, срок 8 часов, без refresh-token в MVP. Frontend и API за одним origin, HTTPS; для изменяющих запросов токен CSRF в заголовке. Пароли — штатный поддерживаемый хэшер платформы, без собственного алгоритма; ошибки входа одинаковы, ограничение частоты попыток. Logout отзывает сессию; блокировка пользователя действует на последующие запросы. Выбор cookie вместо JWT требует согласования; JWT добавит управление отзывом/хранением токенов.

## 5. Процесс и статусы

**Предлагаемое устранение противоречий ТЗ:** создавать проект и вводить внешнюю отчётность вправе координатор (раздел 2); приёмочные сценарии раздела 8, где это делает РП, исправить после согласования. До согласования не выдавать эти права двум ролям автоматически.

Project: draft → active → completed; draft/active/completed → archived. Активация и завершение — РП; архивирование — координатор; восстановления и удаления опубликованных проектов в MVP нет. Черновики также не удаляются через API первой версии.

Завершение: есть минимум одно обязательное мероприятие, все обязательные internallyApproved, заполнена actualEndDate. **Это предложение рабочего ТЗ; заказчик описал финальную внешнюю приёмку. До согласования правила завершение заблокировано для реализации.** Предпочтительное для обсуждения строгое правило — все обязательные externalStatus=accepted; если принято оно, одновременно изменить API и приёмку. Завершённый/архивный проект доступен только для чтения.

Activity: planned → inProgress → managerReview → approverReview → internallyApproved. returned → inProgress → managerReview. Исполнитель запускает работу и отправляет; РП принимает первичную проверку; согласующий утверждает. РП или согласующий могут вернуть из своей стадии в returned с непустым комментарием. Обобщённый статус «На проверке» из ТЗ разделён на два API-значения, UI должен показывать стадию.

При submit: actualEndDate заполнена, не раньше старта проекта и не позже сегодняшней даты; если requiresDocument=true — минимум один допустимый документ. requiresDocument по умолчанию true, исключения назначает РП по согласованной методике. Отчёт/факт меняет только исполнитель в inProgress/returned; состав мероприятия и сроки — РП в planned/inProgress/returned. Во время проверки файлы и факт заморожены. Каждая отправка на managerReview создаёт новый cycle (первый — 1); решения прошлого цикла сохраняются. Нельзя согласовать без предыдущей стадии или менять status обычным PATCH.

externalStatus независим: notSent → sent → accepted либо returned; returned → sent. Только координатор, вручную, после internallyApproved. При returned внешняя причина обязательна; сервер переводит Activity в returned, сохраняет прежние файлы/Review. После исправления снова обе внутренние проверки, затем новая ручная отправка. Новая внутренняя приёмка не означает внешнюю. Внешние даты — даты фиксации в приложении, а не выдуманные ответы портала.

План/факт — календарные даты. Срок просрочен, если plannedEndDate < today(Asia/Yekaterinburg) и actualEndDate=null; рабочее ТЗ использует именно отсутствие факта. Позднее выполнение хранится отдельно: actualEndDate > plannedEndDate. День срока не просрочен. Проверка в работе при заполненном факте не считается просрочкой исполнения, хотя может ждать согласования. plannedEndDate ≥ plannedStartDate, дата окончания проекта ≥ startDate; даты мероприятий вне плана проекта отклоняются. Просрочка не блокирует работу.

Прогресс проекта: число internallyApproved / число всех мероприятий ×100, округление до целого; при нуле — 0. Это предложенная метрика внутренней готовности, не федеральная приёмка. Сводка считает active проекты, inProgress, просрочки без факта, обе стадии проверки и 10 ближайших незавершённых сроков; область доступа одинакова со списками.

## 6. Файлы, показатели, отчётность

Предлагаемый лимит из ТЗ — 20 МиБ (20×1024×1024 байт) на файл; PDF, DOCX, XLSX, PNG, JPEG. Проверять размер, расширение, MIME и сигнатуру, для Office — структуру контейнера; не доверять имени клиента. Случайные ключи, запрет обхода каталогов, файлы вне webroot, скачивание attachment с безопасным именем. Не выполнять содержимое. Политика антивирусной проверки и хранения требует решения до реальных загрузок; demo использует только безопасные синтетические файлы. Изменение файлов после утверждения только через возврат. Версии неизменяемы; удаления API MVP нет. Документы вида calculation/confirmation/report/other; типовые обязательные документы уточнить по методике.

Metric хранит план/факт decimal, unit и дату; EconomicEffect — actual/potential/releasedFunds, decimal amount, RUB, период. JSON decimal передавать строкой, до 2 знаков для денег и 4 для KPI. Не складывать разные единицы, периоды и виды эффекта; пустое значение не равно нулю. Отрицательные значения допустимы как результат ухудшения, формулы не вычисляются. Excel хранится приложением, но не исполняется и не парсится в MVP.

CSV UTF-8 с BOM, разделитель ;, экранирование кавычек/переводов строк и защита от формул электронных таблиц для текстовых ячеек с =,+,-,@ и управляющими префиксами. Одна секция строк единой схемы: rowType, projectId, activityId, title, assignee, plannedEndDate, actualEndDate, status, externalStatus, metricName, unit, plan, actual; KPI отдельными строками rowType=metric. Денежный эффект — rowType=effect, вид в metricName, период в title, сумма в actual. XLSX — последующее пожелание. Экспорт использует те же права и фильтры, содержит только выбранный проект.

Аудит: создание/изменение проекта и назначения, сроки/статусы, загрузки, решения, KPI/эффект, внешний статус и архивирование. Время UTC, актор из сессии; клиент не задаёт автора. Политика срока хранения и доступ админа к метаданным требуют согласования.

## 7. Демо, проверка, запуск

Синтетические данные: минимум 2 предприятия, 2 проекта, 6 мероприятий; все пять ролей, отдельные сотрудники обоих предприятий; planned, inProgress, review, returned, approved и просрочка. Имена вымышленные, документы созданы для demo. Начальные пароли генерируются вне репозитория, передаются безопасно; seed повторяемый и не включается для production.

Backend должен подготовить миграции, параметры окружения без секретов, Compose с постоянными томами БД/файлов, healthcheck, инструкцию запуска с чистой машины, резервного копирования и восстановления пары БД+файлы. БД не публикуется в интернет; frontend/API доступны по HTTPS; CORS только точные разрешённые origins. Не класть данные/резервные копии в Git. Сначала чистая БД → миграции → demo → проверки; восстановление проверяется на отдельном экземпляре. Сейчас этих артефактов ещё нет.

Критерии приёмки полного MVP:
- FR-01: вход, выход, неверный пароль, истёкшая/отозванная сессия; пользователь Б не читает/меняет/скачивает данные А.
- FR-02/03: создание координатором, фильтры и редактирование РП; обязательные поля и сохранение после перезапуска.
- FR-04/05: назначения, разрешённые переходы, даты на границе суток, просрочка без факта и факт с опозданием.
- FR-06/07: допустимый файл скачивается; 20 МиБ проходит, больше — нет; неверный тип/чужой UUID/отсутствующий документ отклоняются; обе проверки, возврат и повторный цикл.
- FR-08: ручная отправка/возврат/приёмка, пометка ручного ввода; недопустимые переходы отклонены.
- FR-09: KPI/эффект и Excel сохраняются без автоматического пересчёта.
- FR-10/11: сводка совпадает со списками; CSV содержит мероприятия, KPI и эффект, безопасно открывается, не раскрывает чужие данные.
- FR-12: операции имеют правильного автора и неизменяемую историю.
- Конкурентные изменения: устаревшая version → 409 без потери данных.
- Чистый запуск и ручной сценарий: координатор → РП → исполнитель → РП → согласующий → координатор → сводка/CSV.

Нужны автоматические интеграционные проверки API с PostgreSQL для прав, переходов и конкурентности; unit-проверки дат/валидации; frontend E2E на реальном сервере для основной цепочки. MSW-прохождение отдельно и не заменяет интеграцию. Протокол хранит SHA, окружение, шаги, ожидаемое/фактическое, дефекты. Сейчас тесты не запускались, приложение не создано.

## 9. Шаблон ответа backend-разработчика

- Проверенная версия/SHA документации:
- Итог: можно согласовать / нужны изменения (это ещё не разрешение начать код).
- Архитектура: замечание → обоснование → более простая альтернатива.
- Модель данных: связи, ограничения, индексы, отсутствующие поля.
- API: путь/DTO → проблема → предлагаемая точная замена.
- Противоречия требований: источник/раздел → вопрос → владелец решения.
- Безопасность и риски: вероятность/последствие → мера → остаточный риск.
- Оценка: задача P0/P1/P2 → часы/диапазон → зависимость; суммарная доступная ёмкость.
- Что реально успевает к КТ, что переносится и почему:
- Решения D1–D10: принято/отклонено/вопрос; кем и когда подтверждено.
- Согласование с frontend: участник, дата, ссылка на обсуждение.
- Фиксация: PR и SHA согласованного API; список изменений MSW.
- Блокеры перед программированием и следующий шаг:
